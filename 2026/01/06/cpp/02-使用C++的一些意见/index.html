# 使用 C++ 的一些意见

  1. 使用构造函数构建不变式
  2. 配合使用构造 / 析构函数来简化资源管理 (RAII)
  3. 避免 “裸的” new 和 delete
  4. 使用容器和算法而不是内置数组和专用代码
  5. 优先使用标准库特性而非自己开发的代码，例如，通过参数化或类层次
  6. 无关的想法应用独立的代码表达，例如，避免类之间的相互依赖
  7. C++ 并不只是面向对象的
  8. C++ 并不只是用于泛型编程
  9. 优选可以进行静态检查的方案
  10. 领资源是显式的（将他们表示为类对象）
  11. 使用库，特别是标准库，不要试图从头开始构建所有的东西
  12. 简单的想法应简单表达
  13. 使用类型丰富的程序设计风格
  14. 底层代码不一定高效；不要因为担心性能问题而回避类、模板和标准库组件
  15. 如果数据具有不变量，封装它
  16. C++ 并非 C 的简单扩展

# 抽象机制

  1. 直接使用代码表达你的想法
  2. 在代码中直接定义类来表示应用中的概念
  3. 用具体类表示那些简单的概念或性能关键的组件
  4. 避免 “裸的” new 和 delete 操作
  5. 用资源句柄和 RAII
  6. 当接口和实现需要完全分离时使用抽象类型作为接口
  7. 实用类层次时，注意区分实现继承和接口继承
  8. 在设计类层次时，注意区分实现继承和接口继承
  9. 控制好对象的构造、拷贝、移动和析构操作
  10. 以值的方式返回容器（依赖于移动操作可以提高效率）
  11. 注意强资源安全，也就是说，不要泄露任何你认为是资源的东西
  12. 使用容器保存同类型的集合，将其定义为资源管理模板
  13. 使用函数模板表是通用的算法
  14. 使用包括 lambda 表达式在内的函数对象表示策略和动作
  15. 使用类型别名和模板别名为类似类型或可能在实现中变化的类型提供统一的符号表示法

# 容器和算法

  1. 没有必要对到重来，直接使用标准库是最好的选择
  2. 除非万不得已，大多数时候先考虑使用标准库，再考虑别的库
  3. 标准库绝非万能的
  4. 如果你用到了某些标准库设施，记得吧头文件 #include 加进来
  5. 标准库设施位于名字空间 std 中
  6. 标准库 string 优于 C 风格字符串
  7. iostream 具有类型敏感、类型安全和可扩展等特点。
  8. 与 T [] 相比，vector <T> 、map<K,T> 和 unordered_map<K, T > 更优.
  9. 一定要了解各种标准库容器的设计思想和优缺点
  10. 优先选用 vector 作为你的容器类型
  11. 数据结构应力求小巧
  12. 如果你拿不准会不会越界，记得使用带边界检查的容器。
  13. 用 push_back () 或者 back_insert () 给容器添加元素
  14. 在 vector 上使用 push_back () 要比在数组上使用 realloc () 更好
  15. 在 main () 函数中捕获常见的异常
  16. 了解常用的标准库算法，用他们代替你自己手写的循环
  17. 如果用迭代器实现某算法过于冗长，不放改写成使用容器版本

# 并发与实用功能

  1. 用资源句柄管理资源 (RAII)
  2. 用 unique_ptr 访问多态类型的对象
  3. 用 shared_ptr 访问共享的对象
  4. 用类型安全的机制处理并发
  5. 最好避免共享数据
  6. 不要为了所谓 "效率" 而不经思考、不经测试地选择使用共享数据
  7. 从并发执行任务的角度进行设计，而不是直接从 thread 角度思考
  8. 一个库是否有用，与它的规模和复杂程度无关
  9. 别轻易抱怨程序的效率低下，记得用事实说话
  10. 编写代码是可以显示地令其利用某些类型的属性
  11. 利用正则表达式简化模式匹配任务
  12. 进行数值计算时优先使用库而非语言本身
  13. 用 number_limits 访问数值类型的属性

# 类型与声明

  1. 如果想了解语言更多的细节和权威解释，请翻阅 ISO C++ 标准
  2. 尽量避免不确定的和未定义的行为
  3. 如果某些代码必须依赖于具体实现，记得把他们与程序的其他部分分离开来
  4. 对于字符对应的字符值不要乱做假定
  5. 以 0 开头的整数是八进制的
  6. 不要使用 "魔法常量"
  7. 不要对证书的尺寸妄加猜测
  8. 不要对浮点数的精度和表示范围妄加猜测
  9. 尽量使用普通的 char, 而非 signed char 或则 unsigend char;
  10. 注意带符号类型和无符号类型之间的转换
  11. 在一条声明语句中中只声明一个名字
  12. 常用的、局部的名字尽量短；不常用的、非局部的名字可以长一些
  13. 起的名不要太相似
  14. 对象的名字应该尽量反映对象的含义
  15. 坚持一种统一的命名风格
  16. 避免使用权大写的名字
  17. 作用域宜小不一大
  18. 最好不要在一个作用域以及它的外增作用中使用相同的名字
  19. 使用指明类型声明时做好用 {} 初始化语法去。
  20. 使用 auto 生命最好使用 = 语法
  21. 避免使用未初始化的变量。
  22. 当内置类型被用来表示一个可变事值时，不防给他
  23. 用别名作为类型的同义词；用枚举类型 = 类定义新类型

# 指针、数组与引用

  1. 使用指针时越简单直接越好；
  2. 不要对指针执行稀奇古怪的算术运算；
  3. 注意不要越界访问数组，尤其不要在数组之外的区域写入内容；
  4. 不要使用多维数组，用合适的容器替代它；
  5. 用 nullptr 代替 0 和 NULL；
  6. 与内置的 C 风格数组相比，优先选用容器（比如 vector、array 和 valarray）；。
  7. 优先选用 string，而不是以 0 结尾的 char 数组；
  8. 如果字符串字面值常量中包含太多反斜线，则使用原始字符串；。
  9. const 引用比普通引用更适合作为函数的实参；
  10. 只有当需要转发和移动时才使用右值引用；
  11. 让表示所有权的指针位于句柄类的内部；
  12. 在底层代码之外尽量不要使用 void*；
  13. 用 const 指针和 const 引用表示接口中不允许修改的部分；
  14. 引用比指针更适合作为函数的实参，不过当需要处理 “对象缺失” 的情况时例外；

# 结构、联合与枚举

  1. 用位域表示由硬件决定的数据布局；
  2. 不要天真地认为仅靠把几个值打包在一个字节中就能轻易地优化内存；
  3. 用 union 减少内存空间的使用（表示一组候选项），不要将它用于类型转换；
  4. 用枚举类型表示一组命名的常量；
  5. enum class 比 “普通的” enum 可靠；
  6. 为枚举类型定义一些适当的操作，以便我们能够既安全又便捷地使用它；
  7. 如果想紧凑地存储数据，则把结构中尺寸较大的成员布局在较小的成员之前；

# 语句

  1. 直到有了合适的初始值再声明变量；
  2. 如果可能的话，优先选用 switch 语句而非 if 语句；
  3. 如果可能的话，优先选用范围 for 语句而非普通的 for 语句；
  4. 当存在明显的循环变量时，优先选用 for 语句而非 while 语句；
  5. 当没有明显的循环变量时，优先选用 while 语句而非 for 语句；
  6. 避免使用 do 语句；
  7. 避免使用 goto；
  8. 注释应该简短直接；
  9. 代码能说清楚的事就别放在注释中；
  10. 注释应该表明程序的意图；
  11. 坚持一种缩进风格，不要轻易改变；

# 表达式

  1. 优先使用标准库，然后是其他库，最后才是 “手工打造的代码”；
  2. 尽可能不要使用字符级的输入；
  3. 读取数据的时候，一定要考虑格式错误的可能；
  4. 优先使用合适的抽象概念（类、算法等），然后才考虑直接使用语言功能（比如 int、语句）；
  5. 避免使用复杂的表达式；
  6. 如果对运算符的优先级存疑，可以用括号括起来；
  7. 避免未定义求值顺序的表达式；。
  8. 避免窄化类型转换；。
  9. 定义符号化常量以防止出现 “魔法常量”；

# 选择适当的操作

  1. 与后置运算符相比，建议优先使用前置运算符；
  2. 使用资源句柄避免泄漏、提前删除和重复删除；
  3. 除非万不得已，否则不要把对象放在自由存储上；优先使用作用域内的变量；
  4. 避免使用 “裸 new” 和 “裸 delete”；
  5. 使用 RAII；
  6. 如果需要对操作添加注释，则应该选用命名的函数对象而非 lambda；
  7. 如果操作具有一定的通用性，则应该选用命名的函数对象而非 lambda；
  8. lambda 应该尽量简短；
  9. 出于可维护性和正确性的考虑，通过引用的方式捕获一定要慎之再慎；
  10. 让编译器推断 lambda 的返回类型；
  11. 用 T {e} 构造值；
  12. 避免显式类型转换（强制类型转换）；
  13. 当不得不使用显式类型转换时，尽量使用命名的转换；
  14. 对于数字类型之间的转换，考虑使用运行时检查的强制类型转换，比如 narrow_cast<>（）；

# 函数

  1. 把有用的操作 “打包” 在一起构成函数，然后认真起个名字；
  2. 一个函数应该对应逻辑上的一个操作；
  3. 让函数尽量简短；
  4. 不要返回指向局部变量的指针或者引用；
  5. 如果函数必须在编译时求值，把它声明成 constexpr；
  6. 如果函数无法返回结果，把它设置为 [[noreturn]]；
  7. 对小对象使用传值的方式；
  8. 如果你想传递无须修改的大值，使用传 const 引用的方式；
  9. 尽量通过 return 值返回结果，不要通过参数修改对象；
  10. 用右值引用实现移动和转发；
  11. 如果找不到合适的对象，可以传入指针（nullptr 表示 “没有对象”）；
  12. 除非万不得已，否则不要传递非 const 引用；
  13. const 的用处广泛，程序员应该多用；
  14. 我们认为 char 或者 const char 参数指向的是 C 风格字符串；
  15. 避免把数组当成指针传递；
  16. 用 initializer_list <T> 传递元素类型相同但是元素数量未知的列表（用其他容器也可以）；
  17. 避免使用数量未知的参数（...）；
  18. 当几个函数完成的功能在概念上一致，仅仅是处理的类型有区别时，使用重载；
  19. 在整数类型上重载时，提供一些函数以消除二义性；
  20. 为你的函数指定前置条件和后置条件；
  21. 不要使用宏；
  22. 如果必须使用宏，一定要用很多大写字母组成宏的名字，尽管这样的名字看起来会很丑陋；

# 异常处理

  1. 在设计初期尽早确定异常处理策略；
  2. 当无法完成既定任务时抛出异常；
  3. 用异常机制处理错误；
  4. 为特定任务设计用户自定义异常类型（而非内置类型）；
  5. 如果由于某种原因你无法使用异常，尽量模仿其机制；
  6. 使用层次化异常处理；
  7. 保持异常处理的各个部分尽量简洁；
  8. 不要试图捕获每个函数的每个异常；
  9. 至少提供基本保障；
  10. 除非有足够的理由，否则最好提供强保障；
  11. 让构造函数建立不变式，如果不能，则抛出异常；
  12. 抛出异常前先释放局部资源；
  13. 谨记在构造函数中抛出异常前释放所有已获取的资源；
  14. 如果局部控制结构足以满足要求，不要使用异常；
  15. 用 “资源获取即初始化” 技术管理资源；
  16. 尽量减少使用 try 块；
  17. 并非所有程序都需要异常安全；
  18. 用 “资源获取即初始化” 技术和异常处理程序维护不变式；
  19. 资源句柄优于弱结构化的 finally；
  20. 为你的不变式设计错误处理策略；
  21. 能在编译时检查的东西最好在编译时检查（使用 static_assert）；
  22. 用你的错误处理策略执行不同层级的检查；
  23. 如果函数不会抛出异常，把它声明成 noexcept 的；
  24. 不要使用异常说明；。
  25. 用引用的方式捕获层次体系中的异常；
  26. 并非每个异常都派生自 exception 类；
  27. 让 main（）捕获和报告所有异常；
  28. 销毁信息前先要找到它的替代者；
  29. 在赋值运算中抛出异常前要确保运算对象处于有效状态；
  30. 不要让析构函数抛出异常；
  31. 把普通代码和异常处理代码分离开来；
  32. 当异常发生时，如果由 new 分配的内存尚未被释放将造成内存泄漏，请注意这一点；
  33. 函数如果能抛出一个异常，那么它就会抛出这个异常，遵循这一假设；
  34. 库不应自行终止程序，正确的做法是抛出一个异常然后由调用者决定该怎么做；
  35. 库不应直接输出面向最终用户的错误诊断信息，正确的做法是抛出一个异常然后由调用者决定该怎么做；

# 名字空间

  1. 用名字空间表达逻辑结构；
  2. 将除 main（）之外的所有非局部名字都置于名字空间中；
  3. 设计一个名字空间，以便能方便地使用它避免意外访问到不相关的名字空间；
  4. 不要为名字空间起非常短的名字；
  5. 如必要，使用名字空间别名为长名字空间名提供简写；
  6. 不要给你的名字空间的使用者增加太多符号表示上的负担；
  7. 为接口和实现使用分离的名字空间；
  8. 当定义名字空间成员时使用 Namespace：：member 表示方式；
  9. 用 inline 名字空间支持版本控制；
  10. 将 using 指示用于代码转换、用于基础库（如 std）以及用于局部作用域内；
  11. 不要将 using 指示放在头文件中；

# 源文件与程序

  1. 用头文件表达接口、强调逻辑结构；
  2. 在实现函数的源文件中 #include 声明函数的头文件；
  3. 不要在不同编译单元中定义同名但含义相近却不完全一致的全局实体；
  4. 不要在头文件中定义非内联函数；。
  5. 只在全局作用域和名字空间中使用 #include；
  6. 只 #include 完整的声明；
  7. 使用包含保护；
  8. 在名字空间中 #include C 头文件以避免全局名字；
  9. 令头文件自包含；。
  10. 区分用户接口和实现者接口；
  11. 区分一般用户接口和专家用户接口；
  12. 若代码是用作非 C++ 程序的一部分，则应避免需要运行时初始化的非局部对象；

# 类

  1. 将概念表示为类；
  2. 将类的接口与实现分离；
  3. 仅当数据真的仅仅是数据且数据成员不存在有意义的不变式时才使用公有数据（struct）；
  4. 定义构造函数来处理对象初始化；
  5. 默认将单参数构造函数声明为 explicit；
  6. 将不修改其对象状态的成员函数声明为 const；
  7. 具体类型是最简单的类。只要适用，就应该优先选择具体类型而不是更复杂的类或普通数据结构；
  8. 仅当函数需要直接访问类的表示时才将其实现为成员函数；
  9. 使用名字空间建立类与其辅助函数间的显式关联；
  10. 将不修改对象值的成员函数定义为 const 成员函数；
  11. 若一个函数需要访问类的表示，但并不需要用某个具体对象来调用，建议将其实现为 static 成员函数；

# 构造、清理、拷贝和移动

  1. 应该将构造函数、赋值操作以及析构函数设计为一组匹配的操作；
  2. 使用构造函数为类建立不变式；
  3. 如果一个构造函数获取了资源，那么这个类就需要一个析构函数释放该资源；
  4. 如果一个类有虚函数，它就需要一个虚析构函数；
  5. 如果一个类没有构造函数，它可以进行逐成员初始化；
  6. 优先选择使用 {} 初始化而不是 = 和（）初始化；
  7. 当且仅当类对象有 “自然的” 默认值时才为类定义默认构造函数；
  8. 如果一个类是一个容器，为它定义一个初始化器列表构造函数；
  9. 按声明顺序初始化成员和基类；
  10. 如果一个类有一个引用成员，它可能需要拷贝操作（拷贝构造函数和拷贝赋值操作）；
  11. 在构造函数中优先选择成员初始化而不是赋值操作；
  12. 使用类内初始化器来提供默认值；
  13. 当编写一个拷贝构造函数时，小心拷贝每个需要拷贝的元素（小心默认初始化器）；
  14. 一个拷贝操作应该提供等价性和独立性；
  15. 小心纠缠的数据结构；
  16. 优先选择移动语义和写前拷贝而不是浅拷贝；
  17. 如果一个类被用作基类，防止切片现象；
  18. 如果一个类需要一个拷贝操作或一个析构函数，它可能需要一个构造函数、一个析构函数、一个拷贝赋值操作以及一个拷贝构造函数；
  19. 如果一个类有一个指针成员，它可能需要一个析构函数和非默认拷贝操作；
  20. 如果一个类是一个资源句柄，它需要一个构造函数、一个析构函数和非默认拷贝操作；
  21. 如果一个默认构造函数、赋值操作或析构函数是恰当的，让编译器自动生成它（不要自己重新编写）；
  22. 显式说明你的不变式；用构造函数建立不变式，用赋值操作保持不变式；
  23. 确保拷贝赋值操作能安全进行自赋值；
  24. 当向类添加一个新成员时，检查用户自定义构造函数是否需要更新，以便初始化新加入的成员；

# 运算符重载

  1. 定义运算符时应该尽量模仿传统用法；
  2. 如果默认的拷贝操作对于某种类型不适用，应该重新定义或者干脆禁用；
  3. 对于较大的运算对象，选用 const 引用类型；
  4. 对于较大的返回结果，选用移动构造函数；
  5. 对于需要访问类的表示部分的操作，优先将其定义为成员函数；
  6. 反之，对于无须访问类的表示部分的操作，优先将其定义为非成员函数；
  7. 用名字空间把辅助函数和 “它们的” 类结合在一起；
  8. 把对称的运算符定义成非成员函数；
  9. 把需要左值作为其左侧运算对象的运算符定义为成员函数；
  10. 用用户自定义的字面值常量模仿传统用法；
  11. 不要轻易为数据成员提供 “set（）和 get（）函数”，除非从语义上确实需要它们；
  12. 谨慎使用隐式类型转换；
  13. 避免使用丢失部分信息（“窄化”）的类型转换；
  14. 对于同一种类型转换，切勿把它同时定义成构造函数以及类型转换运算符；

# 特殊运算符

  1. 用 operator []（）执行取下标以及通过单个值查询等操作；
  2. 用 operator（）（）执行函数调用、取下标以及通过多个值查询等操作；
  3. 用 operator-->（）解引用 “智能指针”；
  4. 前置优于后置；
  5. 除非万不得已，否则不要定义全局 operator new（）和 operator delete（）；
  6. 为特定类或者类层次体系定义成员函数 operator new（）和 operator delete（），用它们分配和释放内存空间；
  7. 用用户自定义的字面值常量模仿人们习惯的语法表示；
  8. 把字面值常量运算符置于单独的名字空间中以便于用户有选择地使用；
  9. 在大多数应用场合，建议使用标准库 string 而非你自己的版本；
  10. 如果需要使用非成员函数访问类的表示（比如改进写法，或者同时访问两个类的表示），把它声明成类的友元；
  11. 当需要访问类的实现时，优先选用成员函数而非友元函数；

# 派生类

  1. 避免使用类型域；
  2. 通过指针和引用访问多态对象；
  3. 使用抽象类，以便聚焦于清晰接口的设计应该提供什么；
  4. 在大型类层次中用 override 显式说明覆盖；
  5. 谨慎使用 final；
  6. 使用抽象类说明接口；
  7. 使用抽象类保持实现细节和接口分离；
  8. 如果一个类有虚函数，那么它也应该有一个虚析构函数；
  9. 抽象类通常不需要构造函数；
  10. 优先选择 private 成员用于类的细节实现；
  11. 优先选择 public 成员用于接口；
  12. 仅在确实需要时才使用 protected 成员，且务必小心使用；
  13. 不要将数据成员声明为 protected；

# 层次类

  1. 为了避免忘记 delete 用 new 创建的对象，建议使用 unique_ptr 或者 shared_ptr；
  2. 不要在作为接口的基类中放置数据成员；。
  3. 用抽象类表示接口；
  4. 为抽象基类定义一个虚析构函数确保其正确地清理资源；
  5. 在规模较大的类层次中用 override 显式地覆盖；
  6. 用抽象类支持接口继承；
  7. 用含有数据成员的基类支持实现继承；
  8. 用普通的多重继承表示特征的组合；
  9. 用多重继承把实现和接口分离开来；
  10. 用虚基类表示层次中一部分（而非全部）类公有的内容；

# 运行时类型信息

  1. 使用虚函数确保无论用什么接口访问对象都执行相同的操作；
  2. 如果在类层次中导航不可避免，使用 dynamic_cast；
  3. 使用 dynamic_cast 进行类型安全的显式类层次导航；
  4. 使用 dynamic_cast 转换引用类型，当无法转换到所需类时，会被认为是一个错误；
  5. 使用 dynamic_cast 转换指针类型，当无法转换到所需类时，只会被认为是一个不同的合法结果；
  6. 用双重分发或访客模式表达基于两个动态类型的操作（除非你需要优化性能）；
  7. 在构造和重构过程中不要调用虚函数；
  8. 使用 typeid 实现扩展的类型信息；
  9. 使用 typeid 查询对象的类型（但不要用它查询对象的接口）；
  10. 优选虚函数而不是基于 typeid 或 dynamic_cast 的重复的 switch 语句；

# 模板

  1. 使用模板表示用于很多实参类型的算法；
  2. 使用模板表示容器；
  3. 注意 template <class T> 和 template <typename T> 含义相同；
  4. 当设计一个模板时，首先设计并调试非模板版本；随后通过添加参数将其泛化；
  5. 模板是类型安全的，但类型检查的时机太晚了；
  6. 当设计一个模板时，仔细思考概念 —— 它对模板实参的要求；
  7. 如果一个类模板必须是可拷贝的，为它定义一个非模板拷贝构造函数和一个非模板拷贝赋值运算符；
  8. 如果一个类模板必须是可移动的，为它定义一个非模板移动构造函数和一个非模板移动赋值运算符；
  9. 虚函数成员不能是模板成员函数；
  10. 只有当一个类型依赖类模板的所有实参时才将其定义为模板成员；
  11. 使用函数模板推断类模板实参类型；
  12. 对多种不同实参类型，重载函数模板来获得相同的语义；
  13. 借助实参代入失败机制为程序提供正确的候选函数集；
  14. 使用模板别名简化符号、隐藏实现细节；
  15. C++ 不支持模板分别编译：在每个用到模板的编译单元中都 #include 模板定义；
  16. 使用普通函数作为接口编写不能用模板处理的代码；
  17. 将大的模板和较严重依赖上下文的模板分开编译；

# 泛型编程

  1. 模板可传递实参类型而不丢失信息；
  2. 模板提供了一种编译时编程的通用机制；
  3. 模板提供了编译时 “鸭子类型”；
  4. 通过 “提升” 具体实例来设计泛型算法；
  5. 用概念说明模板实参要求来泛化算法；
  6. 不要赋予常规符号非常规含义；
  7. 将概念用作设计工具；
  8. 使用常用且规范的模板实参要求来追求算法和实参类型间的 “插头兼容性” 目标；
  9. 发现概念的方法：最小化一个算法对其模板实参的要求，然后推广至更广用途；
  10. 一个概念不仅是一个特定算法实现需求的描述；
  11. 模板实参的默认概念是 Regular；
  12. 并非所有模板实参类型都满足 Regular；
  13. 用代码具体化概念；
  14. 将概念表达为编译时谓词（constexpr 函数）并用 static_asser t（）或 enable_if<> 测试它们；
  15. 将公理用作设计工具；
  16. 将公理作为测试的指导；
  17. 某些概念涉及两个或更多模板实参；
  18. 概念不仅是类型的类型；
  19. 概念可能涉及数值实参；
  20. 将概念作为测试模板定义的指导；

# 特例化

  1. 使用模板提高类型安全；
  2. 使用模板提高代码抽象水平；
  3. 使用模板提供灵活高效的类型和算法参数化；
  4. 记住，值模板实参必须是编译时常量；
  5. 使用函数对象作为类型实参，从而实现 “策略化” 的类型和算法参数化；
  6. 使用默认模板实参为简单使用提供简单符号表示；
  7. 为非常规类型（如数组）进行模板特例化；
  8. 利用模板特例化优化重要实例；
  9. 在任何特例化版本之前声明主模板；
  10. 特例化版本的定义必须位于对其所有使用都可见的作用域中；

# 实例化

让编译器 / 实现在需要时生成特例化版本；
如果需要精确控制实例化环境，使用显式实例化；
如果需要优化生成特例化所需的时间，使用显式实例化；
在模板定义中避免微妙的上下文依赖；
名字必须在模板定义点的作用域中，或是可通过实参依赖查找（ADL）找到；
在实例化点之间保持绑定上下文不变；
避免完全通用的模板可被 ADL 找到；
使用概念或 static_assert 避免选择不恰当的模板；
使用 using 声明限制 ADL 触及的范围；
恰当地使用 -> 或 T：：限定来自模板基类的名字；

# 模板和类层次

  1. 当需要用代码表达一个通用概念时，仔细思考是将它表达为一个模板还是一个类层次；
  2. 一个模板通常为多种实参提供了公共代码；
  3. 抽象类能彻底隐藏实现细节，使其不为用户所见；
  4. 非常规实现通常最好表达为派生类；
  5. 如果不需要显式使用自由存储空间，模板比类层次更有优势；
  6. 如果内联很重要，则模板比抽象类有优势；
  7. 模板接口可以很容易地用模板参数类型表达；
  8. 如果需要进行运行时解析，则类层次是必需的；
  9. 模板和类层次的组合通常优于两者单独使用；
  10. 将模板理解为类型生成器（以及函数生成器）；
  11. 由相同模板生成的两个类之间没有必然联系；
  12. 不要混用类层次和数组；
  13. 不要简单模板化大的类层次；
  14. 一个模板可用来为一个单一（弱类型的）实现提供类型安全的接口；
  15. 模板可用来构成类型安全且紧凑的数据结构；
  16. 模板可用来线性化类层次（最小化空间和访问时间）；

# 元编程

  1. 使用元编程提高类型安全；
  2. 使用元编程将计算移至编译时，从而提高性能；
  3. 避免过度使用元编程导致编译速度严重下降；
  4. 从编译时求值和类型函数的角度思考问题；
  5. 使用模板别名作为返回类型的类型函数的接口；
  6. 使用 constexpr 函数作为返回（非类型）值的类型函数的接口；
  7. 使用萃取非侵入式地关联类型与其属性；
  8. 使用 Conditional 在两个类型之间进行选择；
  9. 使用 Select 在多个类型之间进行选择；
  10. 使用递归表达编译时迭代；
  11. 对运行时无法很好完成的任务使用元编程；
  12. 使用 Enable_if 有条件地声明函数模板；
  13. Enable_if 可以用于很多谓词，概念就在其中那些最有用的谓词中；
  14. 当你需要一个接受实参数量、类型不定的函数时，使用可变参数模板；
  15. 不要对相同类型实参列表使用可变参数模板（更好的方式是初始化器列表）；
  16. 当需要参数转发时，使用可变参数模板和 std：：move（）；
  17. 使用简单元编程实现高效、优雅的单位系统（可进行细粒度的类型检查）；
  18. 使用用户自定义字面值常量简化单位的使用；

# 一个矩阵设计

  1. 列出基本使用情况；
  2. 始终提供输入输出操作以简化简单测试（如单元测试）；
  3. 小心列出程序、类或库在理想情况下应该具有哪些性质；
  4. 列出程序、类或库超出项目范围的性质；
  5. 当设计容器模板时，小心考虑对元素类型的要求；
  6. 考虑如何将运行时检查（如用于调试的检查）纳入设计中；
  7. 设计类时尽可能模仿已有的专业的符号表示方式和语义；
  8. 确保设计中不存在资源泄漏（例如，每个资源有唯一所有者并使用 RAII）；
  9. 考虑如何构造和拷贝类；
  10. 提供完整、灵活、高效且语义明确有效的元素访问操作；
  11. 将实现细节放置在自己的_impl 名字空间中；
  12. 将不要求直接访问类表示形式的常见操作实现为辅助函数；
  13. 为了快速访问数据，保持数据紧凑存储并使用访问器对象来提供必要的复杂访问操作；
  14. 数据结构通常可以用嵌套初始化器列表的形式表达；
  15. 当处理数值时，始终考虑 “终止情况”，例如零和 “很多”；
  16. 除了单元测试和检测代码是否符合要求之外，还要使用实际应用例子来对设计进行测试；
  17. 考虑如何将不常见的严格性能要求纳入设计中；

# 标准库预览

  1. 使用标准库组件保持可移植性；
  2. 使用标准库组件尽量减少维护成本；
  3. 将标准库组件作为更广泛和更专门化的库的基础；
  4. 使用标准库组件作为灵活、广泛使用的软件的模型；
  5. 标准库组件定义在命名空间 std 中，都是在标准库头文件中定义的；
  6. 每个 C 标准库头文件 X.h 都有其 C++ 标准库对应的版本 <cX> ；
  7. 必须 #include 相应的头文件才能使用标准库组件；
  8. 为了对内置数组使用范围 for，需要 #include <iterator> ；
  9. 优选基于异常的错误处理而非返回错误码方式的错误处理；
  10. 始终要捕获 exception&（对标准库和语言支持的异常）和…（对意料之外的异常）；
  11. 标准库 exception 层次可以（但不是必须支持）用于用户自定义异常；
  12. 如果发生严重错误，调用 terminate（）；
  13. 大量使用 static_assert（）和 assert（）；
  14. 不要假定 assert（）总是会被求值；
  15. 如果不能使用异常，考虑使用 <system_error>；

# STL 容器

  1. 一个 STL 容器定义一个序列；
  2. 将 vector 作为默认容器使用；
  3. insert（）和 push_back（）这样的插入操作在 vector 上通常比在 list 上更高效；
  4. 将 forward_list 用于通常为空的序列；
  5. 当涉及性能时，不要盲目信任你的直觉，而要进行测试；
  6. 不要盲目信任渐进复杂性度量；某些序列很短而单一操作的代价差异可能很大；
  7. STL 容器都是资源句柄；
  8. map 通常实现为红黑树；
  9. unordered_map 是哈希表；
  10. STL 容器的元素类型必须提供拷贝和移动操作；
  11. 如果你希望保持多态行为，使用指针或智能指针的容器；
  12. 比较操作应该实现一个严格弱序；
  13. 以传引用方式传递容器参数，以传值方式返回容器；
  14. 对一个容器，用（）初始化器语法初始化大小，用 {} 初始化器语法初始化元素列表；
  15. 用范围 for 循环或首尾迭代器对容器进行简单遍历；
  16. 如果不需要修改容器元素，使用 const 迭代器；
  17. 当使用迭代器时，用 auto 避免冗长易错的输入；
  18. 用 reserve（）避免指向容器元素的指针和迭代器失效；
  19. 未经过测试不要假定 reserve（）会有性能收益；
  20. 使用容器上的 push_back（）或 resize（），而不是数组上的 realloc（）；
  21. vector 和 deque 改变大小后，不要继续使用其上的迭代器；
  22. 在需要时使用 reserve（）令性能可预测；
  23. 不要假定 [] 会进行范围检查；
  24. 当需要保证进行范围检查时使用 at（）；
  25. 用 emplace（）方便符号表示；
  26. 优选紧凑连续存储的数据结构；
  27. 用 emplace（）避免提前初始化元素；
  28. 遍历 list 的代价相对较高；31.4.2 节。
  29. list 一般会有每元素四个字的额外内存开销；
  30. 有序容器序列由其比较对象（默认为 <）定义；
  31. 无序容器（哈希容器）序列并无可预测的序；
  32. 如果你需要在大量数据中快速查找元素，使用无序容器；
  33. 对无自然序的元素类型（例如，无合理的 < 运算符），使用无序容器；
  34. 如果需要按顺序遍历元素，使用有序关联容器（如 map 和 set）；
  35. 用实验检查你的哈希函数是否可接受；
  36. 用异或操作组合标准哈希函数得到的哈希函数通常有很好的性能；
  37. 0.7 通常是一个合理的装载因子；
  38. 你可以为容器提供其他接口；
  39. STL 适配器不提供对其底层容器的直接访问；

# STL 算法

  1. STL 算法操作一个或多个序列；
  2. 一个输入序列是一个半开区间，由一对迭代器定义；
  3. 进行搜索时，算法通常返回输入序列的末尾位置表示 “未找到”；
  4. 优选精心说明的算法而非 “随意代码”；
  5. 当你要编写一个循环时，思考它是否可以表达为一个通用算法；
  6. 确保一对迭代器实参确实指定了一个序列；
  7. 当迭代器对风格显得冗长时，引入容器 / 范围版本的算法；
  8. 用谓词和其他函数对象赋予标准算法更宽泛的含义；
  9. 谓词不能修改其实参；
  10. 指针上默认的 == 和 < 极少能满足标准算法的需求；
  11. 了解你使用的算法的时间复杂性，但要记住复杂性评价只是对性能的粗略导引；
  12. 只在对一个任务没有更专用的算法时使用 for_each（）和 transform（）；
  13. 算法并不直接向其实参序列添加元素或从其中删除元素；
  14. 如果不得不处理未初始化的对象，考虑 uninitialized_* 系列算法；
  15. STL 算法基于其排序比较操作实现相等性比较，而不是使用 ==；
  16. 注意，排序和搜索 C 风格的字符串要求用户提供一个字符串比较操作；

# STL 迭代器

  1. 一个输入序列由一对迭代器定义；
  2. 一个输出序列由单一迭代器定义；程序员应负责避免溢出；
  3. 对任意迭代器 p，[p：p）是一个空序列；
  4. 使用序列尾表示 “未找到”；
  5. 将迭代器理解为更通用、通常行为也更良好的指针；
  6. 使用迭代器类型，如 list <char> ：：iterator，而不是指向容器中元素的指针；
  7. 用 iterator_traits 获取迭代器的相关信息；
  8. 可以用 iterator_traits 实现编译时分发；
  9. 用 iterator_traits 实现基于迭代器类别选择最优算法；
  10. iterator_traits 属实现细节；对它们的使用优选隐式方式；
  11. 用 base（）从 reverse_iterator 提取 iterator；
  12. 可以使用插入迭代器向容器添加新元素；
  13. move_iterator 可用来将拷贝操作变为移动操作；
  14. 确认你的容器可用范围 for 语句遍历；
  15. 用 bind（）创建函数和函数对象的变体；
  16. 注意 bind（）会提前解引用；如果你希望推迟解引用，使用 ref（）；
  17. 可使用 mem_fn（）或 lambda 将 p->f（a）调用规范转换为 f（p，a）；
  18. 如果你需要一个可以保存各种可调用对象的变量，使用 function；

# 资源和内存

  1. 当你需要一个具有 constexpr 大小的序列时，使用 array；34.2.1 节。
  2. 优先选择 array 而不是内置数组；34.2.1 节。
  3. 当你需要 N 个二进制位而 N 又不一定是整数类型的位宽时，使用 bitset；34.2.2 节。
  4. 避免使用 vector <bool> ；34.2.3 节。
  5. 当使用 pair 时，考虑使用 make_pair（）进行类型推断；34.2.4.1 节。
  6. 当使用 tuple 时，考虑使用 make_tuple（）进行类型推断；34.2.4.2 节。
  7. 使用 unique_ptr 表示互斥所有权；34.3.1 节。
  8. 使用 shared_ptr 表示共享所有权；34.3.2 节。
  9. 尽量不使用 weak_ptr；34.3.3 节。
  10. （仅）当由于逻辑上或性能上的原因，常用的 new/delete 语义不能满足需求时才使用分配器；34.4 节。
  11. 优先选择有特定语义的资源句柄而不是智能指针；34.5 节。
  12. 优先选择 unique_ptr 而不是 shared_ptr；34.5 节。
  13. 优先选择智能指针而不是垃圾收集；34.5 节。
  14. 为通用资源的管理提供一致、完整的策略；34.5 节。
  15. 在大量使用指针的程序中处理泄漏问题，垃圾收集是非常有用的；34.5 节。
  16. 垃圾收集是可选的；34.5 节。
  17. 不要伪装指针（即使你不使用垃圾收集）；34.5 节。
  18. 如果你使用垃圾收集，使用 declare_no_pointers（）令垃圾收集器忽略不可能包含指针的数据；见 34.5 节。
  19. 不要随意使用未初始化内存，除非你确实必须这么做；34.6 节。

# 工具

  1. 用 <chrono> 组件，如 steady_clock、duration 和 time_point 进行计时；
  2. 优先使用 <clock> 组件而不是 <ctime> 组件；
  3. 用 duration_cast 获得已知单位的时间段；
  4. 用 system_clock：：now（）获得当前时间；
  5. 可以在编译时查询类型的属性；
  6. 仅当 obj 的值不再使用时使用 move（obj）；
  7. 用 forward（）进行转发；

# 字符串

  1. 使用字符分类而非手工编写的代码检查字符范围；
  2. 果实现类字符串的抽象，使用 character_traits 实现字符上的操作；
  3. 用 basic_string 创建任意字符类型的字符串；
  4. string 用作变量和成员而非基类；
  5. 先选择 string 操作而非 C 风格字符串函数；
  6. 传值方式返回 string（依赖移动语义）；
  7. string：：npos 表示 “string 剩余部分”；
  8. 要将 nullptr 传递给接受 C 风格字符串的 string 函数；
  9. tring 可以按需增长和收缩；
  10. 当需要进行范围检查时，使用 at（）而非迭代器或 []；
  11. 当需要优化速度时，使用迭代器或 [] 而非 at（）；
  12. 如果使用 string，应在程序某些地方捕获 length_error 和 out_of_range；
  13. （仅）在必要时，用 c_str（）生成 string 的 C 风格字符串表示；
  14. string 输入是类型敏感的且不会溢出；
  15. 优先选择 string_stream 或通用的值抽取函数（例如 to <X> ）而非直接使用 str * 系列数值转换函数；
  16. 使用 find（）操作在 string 中定位元素（而不是自己编写循环）；
  17. 直接或间接使用 substr（）读取子串，用 replace（）写入子串；

# 正则表达式

  1. 将 regex 用于正则表达式的大部分常规用途；
  2. 我们可以调整正则表达式符号表示，来适应不同的标准；
  3. 默认正则表达式符号表示为 ECMAScript；
  4. 出于可移植性考虑，使用字符类别符号表示来避免非标准的简写；
  5. 使用正则表达式要注意节制，它很容易变成一种难读的语言；
  6. 优先选择裸字符串字面常量描述模式（最简单的模式除外）；
  7. 注意，\i 符号允许你用之前的子模式来描述后面的一个子模式；
  8. 用？令模式的匹配采用 “懒惰” 策略；
  9. regex 可以使用 ECMAScript、POSIX、awk、grep 和 egrep 符号表示；
  10. 保存模式字符串的一份副本，以备你需要输出它时使用；
  11. 用 regex_search（）在字符流中查找模式，用 regex_match（）查找特定字符串；

# I/O 流

  1. 若用户自定义类型的值存在有意义的文本表示，可为其定义 <<和>>；
  2. 用 cout 进行正常输出，用 cerr 输出错误；
  3. 标准库提供了普通字符和宽字符的 iostream，你可以为任意类型的字符定义 iostream；
  4. 标准库为标准 I/O 流、文件和 string 定义了标准 iostream；
  5. 不要尝试拷贝一个文件流；
  6. 二进制 I/O 依赖于系统；
  7. 在使用文件流之前记得检查它是否已关联到文件；
  8. 优先选择 ifstream 和 ofstream 而非通用的 fstream；
  9. 用 stringfstream 进行内存中的格式化；
  10. 用异常机制捕获稀少的 bad（）-I/O 错误；
  11. 用流状态 fail 处理潜在的可恢复 I/O 错误；
  12. 为了定义新的 <<和>> 你无需修改 istream 或 ostream；
  13. 当实现 iostream 原语操作时，使用 sentry；
  14. 优先选择格式化输入而非未格式化的、底层的输入；
  15. 读取输入存入 string 不会导致溢出；
  16. 当使用 get（）、getline（）和 read（）时，要小心结束标准；

  17. 默认忽略空白符；38.4.1 节。

  18. 你可以定义行为类似虚函数的 <<（或>>），其行为由其第二个运算对象所决定；
  19. 优先选择操纵符而非状态标志来控制 I/O；38.4.3 节。
  20. 如果你希望混合 C 风格 I/O 和 iostream-I/O，使用 sync_with_stdio（true）；
  21. 使用 sync_with_stdio（false）优化 iostream；
  22. 连接流来实现交互式 I/O；
  23. 用 imbue（）来令 iostream 反映 locale 的 “文化差异”；
  24. width（）说明只应用于紧接着的下一个 I/O 操作；
  25. precision（）说明应用于后续所有浮点输出操作；
  26. 浮点格式说明（如 scientific）应用于后续所有浮点输出操作；
  27. 为使用接受参数的标准操纵符，要 #include <iomanip> ；
  28. 你几乎不会需要 flush（）；
  29. 除非可能有审美趣味上的原因，否则不要使用 endl；
  30. 如果 iostream 格式化变得令人厌烦，编写你自己的操纵符；
  31. 通过定义一个简单的函数对象，你可以实现三元运算符的效果（和效率）；

# 区域设置

  1. 做好每个与用户直接交互的重要程序或系统都会在多个不同国家使用的准备；
  2. 不要假定每个人都像你一样使用相同的字符集；
  3. 优先使用 locale 为文化敏感的 I/O 编写专门的代码；
  4. 使用 locale 满足外部（非 C++）标准的需求；
  5. 将 locale 视为 facet 的容器；
  6. 避免在程序文本中嵌入 locale 名字字符串；
  7. 保持仅在程序中少数地方修改 locale；
  8. 尽量少使用全局格式信息；
  9. 优先选择 locale 敏感的字符串比较和排序；
  10. 令 facet 不可变；
  11. 令 locale 处理 facet 的生命周期；
  12. 你可以创建自己的 facet；
  13. 当编写 locale 敏感的 I/O 函数时，记得处理来自用户提供的（覆盖）函数的异常；
  14. 如果需要在数值内使用分隔符，使用 numput；
  15. 使用简单 Money 类型保存货币值；
  16. 使用简单用户自定义类型保存要求 locale 敏感 I/O 的值（而不是将其与内置类型值进行转换）；
  17. facet time_put 既可用于 <chrono> 风格的时间，也可用于 <ctime> 风格的时间；
  18. 在显式使用 locale 时，优先选择字符分类函数；

# 数值计算

1. 数值问题常常很微妙。如果你对一个数值问题的数学内核不是 100% 确定，应接受专家建议或者做一些实验，或者两者都做；
2. 根据用途恰当选择数值类型的变体；
3. 用 numeric_limits 检查数值类型是否满足其用途的需求；
4. 为用户自定义数值类型特例化 numeric_limits；
5. 优先选择 numeric_limits 而不是数值限制宏；
6. 用 std：：complex 进行复数运算；
7. 用 {} 初始化避免窄化；
8. 当运行时效率比操作和元素类型角度的灵活性更重要时，使用 valarray 实现数值计算；
9. 用切片而不是循环表达数组一部分的运算；
10. 切片是访问紧凑数据的很有用的通用抽象；
11. 在手工编写循环实现从序列计算值之前，首先考虑使用 accumulate（）、inner_product（）、partial_sum（）和 adjacent_difference（）；
12. 将引擎绑定到分布，来获得所需的随机数发生器；
13. 要小心谨慎，令你的随机数发生器足够随机；
14. 如果你需要真正的随机数（而不只是一个伪随机序列），使用 random_device；
15. 优先选择产生特定分布的随机数类而不是直接使用 rand（）；

# 并发

  1. 用并发提高响应能力或吞吐率；
  2. 只要代价可接受，应在尽可能高的抽象层次上编程；
  3. 优先选择 packaged_task 和 future，而不是直接使用 thread 和 mutex；
  4. 除非是实现简单计数器，否则优先选择 mutex 和 condition_variable，而不是直接使用 atomic；
  5. 尽量避免显式共享数据；
  6. 将进程视为线程的替代；
  7. 标准库并发特性是类型安全的；
  8. 内存模型是为了省去程序员从机器体系结构层次思考计算机的麻烦；
  9. 内存模型令内存行为大致如我们的朴素预期；
  10. 不同线程访问一个 struct 的不同位域可能相互干扰；
  11. 避免数据竞争；
  12. 原子类型和操作可实现无锁编程；
  13. 无锁编程对避免死锁和确保每个线程持续前进是很重要的；
  14. 将无锁编程留给专家；
  15. 将放松内存模型留给专家；
  16. volatile 告知编译器一个对象的值可以被程序之外的东西改变；
  17. C++ 的 volatile 不是一种同步机制；

# 线程和任务

  1. thread 是系统线程的类型安全的接口；
  2. 不要销毁正在运行的 thread；
  3. 用 join（）等待 thread 结束；
  4. 考虑使用 guarded_thread 为 thread 提供 RAII；
  5. 除非不得已，否则不要 detach（）一个 thread；
  6. 用 lock_guard 或 unique_lock 管理互斥量；
  7. 用 lock（）获取多重锁；
  8. 用 condition_variable 管理 thread 间通信；
  9. 从并发执行任务的角度思考，而非直接从 thread 角度思考；
  10. 重视简洁性；
  11. 用 promise 返回结果，从 future 获取结果；
  12. 不要对一个 promise 两次执行 set_value（）或 set_exception（）；
  13. 用 packaged_task 管理任务抛出的异常以及安排返回值；
  14. 用 packaged_task 和 future 表达对外部服务的请求以及等待其应答；
  15. 不要从一个 future 两次使用 get（）；
  16. 用 async（）启动简单任务；
  17. 选择好的并发粒度很困难：依赖实验和测量做出选择；
  18. 尽量将并发隐藏在并行算法接口之后；
  19. 并行算法在语义上可能与解决同一问题的串行解决方案不同（如 pfind_all（）对 find（））；
  20. 有时，串行解决方案比并行版本简单且快速；

# C 标准库

  1. 如果担心资源泄漏，使用 fstream 而不是 fopen（）/fclose（）；
  2. 出于类型安全和扩展性的考虑，优先选择 <iostream> 而不是 <stdlib> ；
  3. 绝不要使用 gets（）或 scanf（"% s"，s）；43.3 节。
  4. 出于资源管理易用性和简单性考虑，使用 <string> 而不是 <cstring> ；
  5. 只对裸内存使用 C 内存管理例程，如 memcpy（）；。
  6. 优先选择 vector 而不是 malloc（）和 realloc（）；。
  7. C 标准库不了解构造函数和析构函数，对此要小心；。
  8. 优先选择 <chrono> 而不是 <ctime> 进行计时；
  9. 考虑到灵活性、易用性和性能，优先选择 sort（）而不是 qsort（）；
  10. 不要使用 exit（），应选择抛出异常；
  11. 不要使用 longjmp（），应选择抛出异常；

# 兼容性

  1. 在使用新特性编写产品级代码前，应先尝试编写小规模程序来测试它是否符合标准以及你所使用的 C++ 实现是否满足性能要求；
  2. 学习 C 时应使用你能获得的最新的、最完整的标准 C 实现；。
  3. C 和 C 的公共子集不是学习 C 的最佳起点；
  4. 优先选择标准特性而不是非标准特性；
  5. 避免使用 throw 说明这样的弃用特性；
  6. 避免使用 C 风格类型转换；
  7. “隐式 int” 已被弃用，因此应显式说明每个函数、变量、const 等的类型；
  8. 在将 C 程序转换为 C++ 程序时，首先确保一致使用函数声明（原型）和标准头文件；
  9. 在将 C 程序转换为 C 程序时，需将与 C 关键字同名的变量改名；
  10. 出于可移植性和类型安全的考虑，如果必须使用 C，应该用 C 和 C++ 的公共子集编写代码；
  11. 在将 C 程序转换为 C++ 程序时，应将 malloc（）的返回结果转换为正确类型或改用 new；
  12. 当从 malloc（）和 free（）转换为 new 和 delete 时，考虑使用 vector、push_back（）和 reserve（）而不是 realloc（）；
  13. 在将 C 程序转换为 C 程序时，记住 C 中没有从 int 到枚举类型的隐式类型转换；如需要，应使用显式类型转换；
  14. 名字空间 std 中定义的特性都是定义于一个文件名无后缀的头文件中（如 std：：cout 声明于 <iostream> 中）；
  15. 包含 <string> 以便使用 std：：string（<string.h> 中都是 C 风格字符串函数）；
  16. 每个标准 C 头文件 <X.h> 都将名字置于全局名字空间中，对应的 C++ 头文件 <cX> 将名字置于名字空间 std 中；
  17. 声明 C 函数时使用 extern “C”；
